# AI 文档编写规范

> 版本：V1.0 | 日期：2026-08-12 | 状态：✅ 生效
> 适用范围：docs 目录下所有文档的编写、修改与维护

本规范定义 docs 目录的结构、格式与维护规则，确保：信息可快速定位、内容不丢失不偏差、文档可维护（与代码同步演进）。

---

## 一、目录结构与命名

### 1.1 层级固定，禁止随意改动

```
docs/
├── README.md             # 唯一入口：项目简介 + 完整索引（新增文件必须在此登记）
├── 00-conventions/       # 规范：开发规范、文档编写规范、评审、引用图
├── 01-architecture/      # 设计：架构总览 + 按模块设计
├── 02-db/                # 数据库：总览 + 约定 + 每表一文档
├── 03-api/               # 接口：总览 + 通用约定 + 每模块接口
├── 04-environments/      # 环境：开发 / 测试 / 生产
├── 05-infrastructure/    # 基础设施与第三方
└── 06-reference/         # 参考资料
```

### 1.2 命名规则

| 对象 | 规则 | 示例 |
|------|------|------|
| 目录 | 数字前缀 + 语义名，保证排序稳定 | `02-db`、`03-api` |
| 文档文件 | 小写连字符（kebab-case），`.md` 后缀 | `rag-retrieval.md`、`ai_memory.md` |
| 每表文档 | 以表名命名，放 `02-db/tables/` | `tables/ai_memory.md` |
| 每模块接口 | 以模块名命名，放 `03-api/modules/` | `modules/knowledge.md` |
| 规划模块 | 放 `modules/planned/`，标记 🚧 | `modules/planned/xxx.md` |

### 1.3 新文件登记

新增任何文档后，**必须**：
1. 在 [docs/README.md](../README.md) 的完整索引中补一行；
2. 在所属层的 `README.md` 中补一行；
3. 在 [reference-map.md](reference-map.md) 中央引用图登记（引用上游）；
4. 反向推导"应引用本新文档"的既有文档并补链（见 4.4）；
5. 头部写元数据块（见第二节）。

## 二、文档头部元数据块（强制）

```markdown
> 版本：V1.0 | 日期：YYYY-MM-DD | 状态：✅ 已实现 / 🚧 规划中 / 📝 草稿
> 事实源：<文件路径>
```

| 字段 | 必填 | 说明 |
|------|:---:|------|
| 版本 | ✅ | 语义化，有实质变更递增 |
| 日期 | ✅ | YYYY-MM-DD |
| 状态 | ✅ | ✅ 已实现 / 🚧 规划中 / 📝 草稿 / ❌ 已废弃 |
| 事实源 | 条件 | 与代码/数据强相关时必须标注 |

## 三、写作格式要求

### 3.1 原则：密集事实 > 叙述散文

- **表格优先**：字段清单、参数清单、枚举、状态流转一律用 Markdown 表格。
- **代码块优先**：JSON 请求/响应、SQL、Key 格式、配置片段用代码块。
- **删叙述**：不要写可推断的废话，直接给事实。
- **字段级完整**：列出的字段必须完整（类型 / 必填 / 默认 / 含义），禁止省略。

### 3.2 状态标记（强制）

| 标记 | 含义 | 用法 |
|------|------|------|
| ✅ | 已实现、可用 | 文档头部状态 + 模块地图 |
| 🚧 | 规划中，代码未实现 | 明确标注，**禁止描述成已上线** |
| 📝 | 草稿待完善 | 未定稿的内容 |
| ❌ | 已废弃 | 保留供追溯，注明替代方案 |

## 四、引用管理与变更影响

> 文档之间是**引用图**关系。改任何一个文档，必须反向找出"谁引用了它"并同步。

### 4.1 中央引用图（reference-map.md）

- 所有文档的引用关系**只在 [reference-map.md](reference-map.md) 登记一处**（单一事实来源）。
- 每行一个文档，「引用」列记录其**上游**（它依赖谁）。
- **反向推导下游**：修改文档 X 时，grep「引用」列含 X 的所有行 → 必须检查/同步的下游文档。

### 4.2 文档类型模板（固定引用结构）

| 文档类型 | 必须引用（上游） | 必须在哪个索引登记 |
|---------|----------------|-------------------|
| 表文档（02-db/tables/） | data-dictionary、conventions、所属模块设计 | 02-db/README 表清单 |
| API 模块文档（03-api/modules/） | common、对应设计文档、对应表文档 | 03-api/README 模块清单 |
| 设计文档（01-architecture/） | overview、相关表文档、相关 API 文档 | 01-architecture/README |
| 环境文档（04-environments/） | 对应配置（事实源）、seed 数据、相关 infra | 04-environments/README |
| 基础设施文档（05-infrastructure/） | 对应源码类/常量类（事实源）、相关设计 | 05-infrastructure/README |
| 层 README | 该层全部文档 | — |
| 根 README | 全部文档（索引） | — |

### 4.3 变更影响矩阵

| 变更类型 | 必须同步的文档 |
|---------|--------------|
| 修改接口 | ① 对应 API 文档 ② common.md（若涉及通用约定） ③ 相关设计文档 ④ 相关表文档 |
| 修改表结构 | ① 对应表文档 ② data-dictionary ③ 表清单 ④ migration ⑤ 引用该表的所有文档（反向推导） ⑥ conventions |
| 修改业务规则 | ① 相关设计 ② 相关 API ③ 相关表 |
| 修改配置/环境变量 | ① environments 对应文档 ② infrastructure 对应文档 ③ CLAUDE.md |
| 新增模块 | ① 新设计文档 ② 新接口文档 ③ 相关表文档 ④ 根 README 模块地图 ⑤ 各层 README |
| **新增文档** | 见 4.4 |
| 修复已知缺陷 | ① 对应文档状态 ✅ ② 缺陷报告标记「已修复」 |

### 4.4 新增文档流程（完整步骤）

1. **套类型模板**（4.2）确定必须引用的上游文档。
2. **在 [reference-map.md](reference-map.md) 登记**：新增一行，填「引用（上游）」。
3. **在根 [README](../README.md) 完整索引登记**一行。
4. **在所属层 README 登记**一行。
5. **反向推导补链**：grep reference-map，为"应引用本新文档"的既有文档补链接。
6. **更新相关模块地图 / 表清单**。
7. **头部写元数据块**。

### 4.5 新功能模块文档同步全流程清单

实现新功能模块时，按 A-D 四段执行（缺一不可）：

**A. 设计与表**
- [ ] ① 设计文档（规划模块先在 planned 定稿）
- [ ] ② 表文档：已存在则状态 🚧→✅；新增则建表 SQL + 新表文档 + 登记表清单
- [ ] ③ 数据字典：字段/枚举有变 → 同步
- [ ] ④ 迁移记录：新增/改表 → 更新版本

**B. 接口**
- [ ] ⑤ 接口文档（已实现 / 规划中分目录）
- [ ] ⑥ 通用约定：新错误码/鉴权 → 更新 common

**C. 索引与引用图**
- [ ] ⑦ reference-map 登记全部新文档
- [ ] ⑧ 反向推导补链
- [ ] ⑨ 根 README 模块地图（🚧→✅）与完整索引
- [ ] ⑩ 各层 README 登记

**D. 收尾**
- [ ] ⑪ 关联文档（安全/基础设施/环境）同步
- [ ] ⑫ 修复的已知缺陷标记「已修复」
- [ ] ⑬ 新文档全部写元数据头

### 4.6 一致性校验

- 修改文档后，检查其「引用」列中的上游是否都有效、是否仍引用它（4.1 反向推导）。
- 删除文档时，必须同步：删除 reference-map 行 + 根 README 索引行 + 所有引用它的文档中的链接。
- 链接与索引完整性可随时用 `grep` / `find` 抽查（无脚本依赖）。

## 五、事实准确性与一致性

### 5.1 单一事实来源

| 主题 | 事实源（以此为准） | 文档角色 |
|------|-------------------|---------|
| 数据库结构 | `src/main/resources/sql/init_schema.sql` | 02-db 文档是契约摘要 |
| 接口契约 | Controller 源码注解（`@RequestMapping`/`@Valid`/DTO） | 03-api 文档是契约摘要 |
| 业务规则 | Service 实现 + 设计文档 | 01-architecture |
| 配置 | `application*.yml` / `intent-gate.yml` | environments + infrastructure |

### 5.2 发现不一致时的处理

- **源码为准**：接口/数据以代码为准，文档落后时更新文档，并同步元数据版本号。

### 5.3 与代码同步（维护硬规则）

- **规则 1**：新增/修改接口、表、业务规则时，同一 PR 必须同步对应文档。
- **规则 2**：删除接口/字段时，同步删除文档对应条目，不允许残留。
- **规则 3**：文档标记的「待完成/规划」事项，落地代码后立即把状态改为 ✅。
